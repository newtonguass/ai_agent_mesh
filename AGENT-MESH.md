# AgentMesh setup and ownership guide

AgentMesh is a Go controller for Istio **sidecar** meshes. It configures captured
outbound HTTP, HTTPS and TCP whitelists and lets explicitly connected meshes
trust approved foreign CAs. It does not join control planes, copy CA private
keys, discover remote services automatically, or replace a network firewall.

This guide is self-contained for an operator or an offline AI agent. Use the
existing development/test workloads directly. Resolve placeholders from the
actual cluster; do not apply the lab's gateway or RBAC settings to an existing
gateway. The separate [TESTING.md](TESTING.md) explains disposable lab creation.

For copyable namespace-only installation commands, use [NAMESPACE-INSTALL.md](NAMESPACE-INSTALL.md).

## Choose one installation mode

| | Cluster-wide CRD mode | Namespace-only ConfigMap mode |
|---|---|---|
| Install | `crd.yaml` and `install.yaml`, once per cluster | `install-namespaced.yaml` in an existing namespace |
| Controller | One replica in an administrator namespace | One replica in the application namespace |
| Inputs | Namespaced AgentMeshEgress / AgentMeshExpose | One local declarations ConfigMap containing egress / expose lists |
| Approved trust | One administrator-selected **cluster-scoped** AgentMeshTrustedBundle | Administrator publishes the approved shared public bundle into a local trust ConfigMap |
| RBAC | ClusterRole and ClusterRoleBinding | Role and RoleBinding only; no CRDs or cluster-scoped RBAC |
| Status | CR `status.conditions` and `status.applicationURLs` | `mesh-access-state` ConfigMap, `data.status.json` |
| Developer grant | Namespace RoleBinding to ClusterRole `agentmesh-developer` | Namespace RoleBinding to Role `agentmesh-developer` |

Do not run two controllers over the same namespace. For a mixed installation,
add namespace-only deployments' namespaces to the cluster controller's
`forbiddenNamespaces`. There is no leader election: use one replica and Recreate.
Both modes require an existing Istio sidecar installation and its networking CRDs.
Namespace mode does not synchronize trust across namespaces. The administrator's
existing GitOps/distribution process must copy the approved shared bundle and
rotate it in every participating namespace.

ConfigMaps are appropriate when installing CRDs or granting cluster access is
unavailable. They trade Kubernetes schema validation, separate object lifecycle
and native CR status for a controller-validated JSON document. AgentMesh validates
both modes before writing a namespace plan; it rejects unknown declaration fields.
The three CRDs remain the richer interface for a cluster-wide installation.

## Build and install

The runtime uses Go's standard library and a single static binary in a `scratch`
image. It has no shell, Python interpreter or external Go module dependencies.
Go 1.25 or newer is required for local builds; the Dockerfile pins Go 1.27.1.

```sh
go test -race ./...
go vet ./...
python3 build.py
# For a normal registry workflow, tag/push using your approved registry:
docker tag mesh-access-controller:dev YOUR_REGISTRY/mesh-access-controller:YOUR_TAG
```

`build.py` is a host-only helper that streams the Docker context and embeds a
SHA-256 identity of the Go sources. A plain `docker build` also works but reports
`development` unless BUILD_ID is supplied. Verification scripts require the
source identity generated by `build.py`. Publish or load the image before rollout.
Replace the image in the chosen install manifest before applying it outside the lab.

For **cluster mode**, an administrator applies `crd.yaml` and `install.yaml`.
The default controller namespace is `agentmesh-system`. If changing it, update
the Namespace, all installation object namespaces and binding subjects together.
The controller's own namespace is excluded from application reconciliation.

For **namespace mode**, replace every `namespace: example` in
`install-namespaced.yaml` with the existing application namespace and apply that
file. It creates no Namespace or cluster-scoped resource. Its controller has
`--mode=namespace`. Settings, declarations, trust and state use four separate
ConfigMaps; the Role allows named GETs on these and PATCH only on state. It cannot
edit any of its inputs. If renaming ConfigMaps, update both arguments/config and
Role resourceNames. The initial declaration lists are empty; the placeholder
trust is unused until MTLS or Expose is declared.

Reapplying the complete namespace install template can overwrite declaration
lists or public trust with placeholders. After initial installation, manage
those ConfigMaps separately using GitOps or targeted updates.

Both modes discover local Services, Pods, ServiceAccounts and workload templates;
read Gateway/VirtualService prerequisites; and manage Sidecar, ServiceEntry,
DestinationRule, VirtualService and EnvoyFilter. They do not read Secrets, write
Services/Gateways, or access AuthorizationPolicy. Workload PATCH is needed for
requester enrollment; it is a broad Kubernetes permission. Admission restrictions
on permitted patches remain a platform responsibility.

## Administrator settings and public trust

`mesh-access-config` contains `data.config.json`. In cluster mode this lives in
the controller namespace; in namespace mode it lives alongside the application.

```json
{
  "schemaVersion": 1,
  "forbiddenNamespaces": ["istio-system", "kube-system", "kube-public", "kube-node-lease"],
  "trustBundle": {"name": "mesh-access-trust"},
  "gateway": {"service": "ingressgateway", "port": 443},
  "exposurePolicy": {"dnsSuffix": "company.example.com", "labelSuffix": "-agent-mesh"}
}
```

The optional exposure naming restrictions require, for example,
`orders-agent-mesh.company.example.com`. They do not authorize callers. Add custom
mesh/system namespaces to the forbidden list. Different gateway Service names or
ports can be supplied in individual Expose declarations. `credentialName` is not
an AgentMesh setting; it belongs to the existing Gateway.

For cluster mode, an administrator creates the one shared selected bundle:

```yaml
apiVersion: agentmesh.io/v1alpha1
kind: AgentMeshTrustedBundle
metadata:
  name: mesh-access-trust
spec:
  caBundle: |
    -----BEGIN CERTIFICATE-----
    REPLACE_WITH_APPROVED_PUBLIC_CA_CERTIFICATE
    -----END CERTIFICATE-----
```

There is **no namespace** on this resource. Concatenate the approved public PEM
certificates. The controller can read the CR and patch its status but cannot
create, edit or delete the bundle spec. The optional `agentmesh-trust-admin`
ClusterRole has no default binding; delegate only to trusted administrators.

For namespace mode, the administrator publishes the same approved public bundle:

```sh
kubectl -n example create configmap mesh-access-trust \
  --from-file=ca.crt=approved-mesh-roots.pem --dry-run=client -o yaml |
  kubectl -n example apply -f -
```

The input key is `ca.crt`. No CA private key, server private key or issuer Secret
belongs in either input. Plain HTTP/HTTPS/TCP egress does not require a bundle.
For MTLS, the source needs the destination server's issuer chain, while the
terminating gateway needs the source workload's issuer chain. Include local roots
where local gateway MTLS or existing accepted clients need them. AgentMesh replaces
the matched validation CA set with this **complete desired bundle**; it does not
implicitly union it with the credential Secret's `ca.crt`.

Istio/cert-manager do not automatically update these AgentMesh inputs. During CA
rotation, the PKI owner distributes old+new public roots, rotates issuers/leaf
certificates, verifies fresh connections, and then removes retired roots. Updating
a valid bundle reconciles filters without restarting the gateway. Existing TLS
sessions can survive a trust update; force new connections for verification.

The limit is 256 KiB of PEM per selected bundle, and 900 KiB per generated object.
Repeated inline roots across requester destinations can hit the object limit
first. This is a validation limit, not a performance guarantee or a safe CA count.
Mounted-file/SDS trust distribution is not implemented here.

## Developer egress declaration

```yaml
apiVersion: agentmesh.io/v1alpha1
kind: AgentMeshEgress
metadata:
  name: agent
  namespace: example
spec:
  serviceAccount: agent-client
  inCluster:
  - host: orders
    port: 8080
    protocol: HTTP
  - host: catalog.catalog-ns.svc.cluster.local
    port: 8080
    protocol: HTTP
  outCluster:
  - host: orders-agent-mesh.remote.example.com
    port: 443
    protocol: MTLS
  - host: api.example.com
    port: 443
    protocol: HTTPS
  - host: db.example.com
    port: 3306
    protocol: TCP
    addresses: [192.0.2.10]
```

| Protocol | Application sends | Captured egress checks / setup |
|---|---|---|
| HTTP | `http://host:port` | Exact authority, case-insensitive, and destination port |
| HTTPS | `https://host:port` | Application TLS; exact SNI and port, plus native Service IP for internal HTTPS |
| MTLS | **`http://host:port`** | Sidecar originates ISTIO_MUTUAL using its own workload certificate; exact remote server DNS SAN and approved CA |
| TCP | Opaque TCP to declared IP/port | Exact destination IP and port; external individual addresses are mandatory |

MTLS does not wrap application HTTPS; doing so sends TLS bytes into an HTTP route.
For HTTPS the application remains responsible for server-certificate verification.
External TCP addresses are static individual IPv4/IPv6 addresses, not CIDRs; DNS
changes are not tracked. UDP, ambient mesh and general TLS passthrough are outside
this controller's contract.

Internal hosts are short local Service names or
`service.namespace.svc.cluster.local`. Local Services must have a ClusterIP and
the declared TCP Service port. Cross-namespace Service addresses are read through
DNS, so namespace mode needs no cross-namespace API grant. Headless and ExternalName
Services are not supported. Internal addresses cannot be overridden.

External HTTP/HTTPS/MTLS may supply `endpoint: dns-name:port` or `IPv4:port` when
network routing differs from the logical host/port. DNS, SNI and HTTP authority
remain the logical host. External host definitions must agree across declarations;
this release supports one external port/protocol definition per host. No wildcard
hosts. Maximum 64 entries per inCluster/outCluster list and 64 TCP addresses each.

Use one Egress per SA per namespace. AgentMesh finds all matching pods by their
actual SA, verifies an Istio proxy exists (including native sidecars), and stamps
Deployment/StatefulSet/DaemonSet templates with its enrollment metadata. Normal
workload rollout installs bootstrap labels; users do not label live pods manually.
This can roll requester pods. Jobs/bare pods require the correct bootstrap metadata
before creation; OnDelete workloads require owner replacement. Give requesters a
separate SA from gateways; AgentMesh rejects enrollment of known gateway workloads.

An empty Egress destination list retains explicit deny-all for **captured** egress.
Deleting the declaration unenrolls the SA and removes the generated whitelist;
it is not a deny-all operation. Application access already granted to an authorized
SA remains available to compromised code in that application's trust boundary.

## Developer exposure declaration: trust only

```yaml
apiVersion: agentmesh.io/v1alpha1
kind: AgentMeshExpose
metadata:
  name: orders
  namespace: example
spec:
  service: orders
  port: 8080
  host: orders-agent-mesh.company.example.com
  gatewaySelector:
    istio: aspe-ingressgateway
  gatewayService: ingressgateway
  gatewayPort: 443
```

`gatewayService` and `gatewayPort` are optional overrides of administrator defaults.
There is **no serviceAccount, allow or credentialName field**. Expose selects an
existing local Service and an existing local gateway. It generates **only one
EnvoyFilter**, with the supplied selector and exact SNI plus resolved listener port.
It does not create, update or delete AuthorizationPolicy. Namespace owners use
Istio's full policy API for principals, methods, paths, claims or external auth.

Prerequisites must already be prepared by the gateway owner:

1. A healthy gateway Deployment/Service in the same namespace. The supplied labels
   must select exactly that Service's gateway pods. AgentMesh does not add labels,
   change its Deployment, Service, RBAC, Secrets, listeners or routes.
2. Exactly one existing Gateway server on the declared gateway Service port with
   that exact hostname, protocol HTTPS and TLS mode MUTUAL. Wildcard-only, SIMPLE
   and PASSTHROUGH servers are rejected. Namespace-prefixed exact Gateway hosts
   such as `example/host` are accepted.
3. A VirtualService bound to that Gateway, with the exact host and an HTTP route
   to the declared backend Service and explicit **Service port**.
4. A valid server certificate with the exposure hostname as DNS SAN and working
   gateway SDS/file credentials. Credential lifecycle and Secret-reading RBAC
   belong to the gateway owner. `fixtures/gateway-rbac.yaml` is lab-only.
5. Owner-managed ingress AuthorizationPolicy and backend policy as required.
   After gateway TLS termination, the backend's TLS peer is the **gateway SA**.
   Check the original requester SA at the gateway, not at the backend.

AgentMesh reads Service targetPort, including named ports on regular/native
containers, to resolve the actual Envoy listener. For Service 443 -> targetPort
8443, the filter matches **8443 + exact SNI**. The existing MUTUAL server enforces
client certificates; the filter changes validation trust. Other HTTPS SNI chains
on the same port remain unaffected by this filter.

Replacing the validation-context oneof can remove old validation defaults.
AgentMesh re-adds owner Gateway subjectAltNames, verifyCertificateSpki and
verifyCertificateHash. Custom SDS validation options and other EnvoyFilters need
separate compatibility review; do not assume every custom TLS configuration is
preserved. AgentMesh does not change server certificate SDS or client-cert enforcement.

Example **owner-managed** authorization, applied independently of AgentMesh:

```yaml
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: orders-requesters
  namespace: example
spec:
  selector:
    matchLabels:
      istio: aspe-ingressgateway
  action: DENY
  rules:
  - from:
    - source:
        notPrincipals: [remote-mesh/ns/example/sa/agent-client]
    to:
    - operation:
        hosts: [orders-agent-mesh.company.example.com, 'orders-agent-mesh.company.example.com:*']
        ports: ['8443']
```

This example denies other authenticated identities on that host; existing Istio
ALLOW/DENY policies also apply. It is not a replacement for reviewing all ingress
paths. A trusted issuer can mint certificates carrying accepted SPIFFE names;
adding a CA grants issuer authority, not just trust in one cluster's claimed name.

## Same-cluster gateway MTLS

Use a native Service with an HTTP-named port to let Istio parse the application's
HTTP and select the MTLS subset. If the existing ingress Service has an HTTPS-named
port, its owner may provide a separate HTTP-named Service alias pointing at the
same gateway pods. AgentMesh does not create or edit that Service.

```yaml
spec:
  serviceAccount: agent-client
  inCluster:
  - host: local-gateway
    port: 443
    protocol: MTLS
    serverName: orders-agent-mesh.company.example.com
```

The requester calls `http://local-gateway:443`. AgentMesh uses the native Service,
creates DR/VS and the requester trust filter, rewrites authority to serverName,
and creates no ServiceEntry. The gateway still needs owner listener/routes/auth.

## Namespace-only declaration format and delegation

Replace CR objects with entries in `data.declarations.json`. Each entry has a
`name` followed by exactly the corresponding Egress or Expose spec fields:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: mesh-access-declarations
  namespace: example
data:
  declarations.json: |
    {
      "schemaVersion": 1,
      "egress": [{
        "name": "agent",
        "serviceAccount": "agent-client",
        "inCluster": [{"host": "orders", "port": 8080, "protocol": "HTTP"}],
        "outCluster": [{"host": "orders-agent-mesh.remote.example.com", "port": 443, "protocol": "MTLS"}]
      }],
      "expose": [{
        "name": "orders", "service": "orders", "port": 8080,
        "host": "orders-agent-mesh.company.example.com",
        "gatewaySelector": {"istio": "aspe-ingressgateway"}
      }]
    }
```

Create a namespace RoleBinding for the developer group, using `kind: Role` for
namespace mode or `kind: ClusterRole` for cluster mode:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: agentmesh-developers
  namespace: example
subjects:
- kind: Group
  name: example-developers
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: agentmesh-developer
  apiGroup: rbac.authorization.k8s.io
```

The namespace developer Role permits get/update/patch on **only the pre-created
declarations ConfigMap**, and get on state. It grants no create/delete/list of
ConfigMaps, no trust/config mutation, and no generated policy or workload writes.
Removing entries revokes their declarations; keep the declarations ConfigMap itself.
Existing broader RBAC grants remain additive. Namespace owners with unrestricted
ConfigMap/workload access can change these inputs indirectly or directly; use
RBAC/admission (for example OPA Gatekeeper) to enforce the intended boundary.

## Observe, update and remove

Reconciliation polls every five seconds, re-reads projected API tokens, paginates
lists and uses resourceVersion/UID preconditions for updates/deletes. Each namespace policy plan
is validated before workload or generated-policy writes. Ownership/status bookkeeping
can still be written for an invalid plan. One bad namespace does not block others in cluster mode.
Generated specs are replaced, so removed roots/destinations disappear; owned drift
is corrected. Conflicting unmanaged names/egress hosts are rejected. Writes and xDS
updates are not transactional.

A malformed declaration, or missing/invalid **required** bundle, reports failure
and retains the last good namespace plan. This can delay revocation: repair invalid
inputs and verify fresh traffic. A missing declarations ConfigMap likewise retains
state. To remove every namespace declaration, submit valid empty lists. An unused
invalid cluster TrustedBundle reports its own failure without blocking active plans.

```sh
# Cluster mode
kubectl -n example get agentmeshegress,agentmeshexpose -o yaml
kubectl get agentmeshtrustedbundle mesh-access-trust -o yaml
kubectl -n agentmesh-system logs deploy/mesh-access-controller
# Namespace mode
kubectl -n example get configmap mesh-access-state -o jsonpath='{.data.status\.json}'
kubectl -n example logs deploy/mesh-access-controller
```

`Configured=True`/`configured:true` means Kubernetes reconciliation succeeded,
not that Envoy accepted xDS or traffic succeeded. Namespace status identifies the
input ConfigMap resourceVersion. Verify source active TLS/SAN/client SDS, gateway
exact SNI/port trust, owner auth positive/negative cases and ordinary HTTPS.
Use [TESTING.md](TESTING.md) and [VERIFICATION.md](VERIFICATION.md) for evidence.

Deleting Expose removes its trust filter; owner Gateway, routes, credentials and
policies remain. This does not close the listener or guarantee access revocation.
For normal uninstall, remove declarations, wait for generated resources and
requester enrollment metadata to be pruned, then remove the controller/RBAC and
ownership ConfigMaps. Never delete a shared CRD to uninstall one namespace.

## Upgrade and migration

Stop old controllers before starting this Go release. Keep existing ownership
ConfigMaps and their UIDs. The persisted internal `mesh-access.example.com/*`
metadata remains intentionally stable even though the public API is agentmesh.io.

Remove `allow` and `credentialName` from Expose and old gateway credentialName
from administrator config. Review existing authorization as an **owner** before
removing any old policy. The Go controller never reads, writes or deletes old
AuthorizationPolicies; removing the old `allow` field does not change those policies.
Earlier generated Gateway/alias Services are untouched. Old `ma-expose-*`
VirtualServices and DestinationRules are excluded from pruning. No legacy gateway
labels are removed and no gateway rollout is triggered.

The owner must adopt retained resources: preserve specs, transfer/remove the old
AgentMesh ownership reference and managed-by label through the owner's workflow.
Deleting their old ConfigMap before adoption can garbage-collect them. Existing
routes must match Expose's declared Service/port; AgentMesh does not retarget them.

Switching CRD mode to ConfigMap mode is a deliberate migration, not automatic
adoption. Stop the old controller for the namespace, exclude it from cluster mode,
copy desired declarations into the JSON format and distribute approved trust.
Preserve or explicitly transfer generated-resource ownerReferences to the new
state ConfigMap UID; otherwise ownership collision checks reject takeover. Prefer
a tested uninstall/reinstall where the development environment permits it. Never
run both controllers while moving ownership.

For old **namespaced TrustedBundle CRDs**, Kubernetes does not allow changing a
CRD's scope in place. Export all old bundles, choose the administrator-approved
shared set, stop old controllers, and explicitly replace only that old bundle CRD.
Deleting it deletes its CRs. Recreate the cluster bundle, preserve Egress/Expose
and local ownership anchors, then install the cluster controller. Migrate older
API groups by copying kind/name/namespace/desired spec to agentmesh.io/v1alpha1;
never copy UID/resourceVersion/status. Retire old CRDs only after migration and
rollback review. The controller performs no CRD migration or deletion.
